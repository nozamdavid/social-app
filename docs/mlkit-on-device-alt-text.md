# Caelum Android: on-device ALT-text assistance

Assessed **2026-11-10**. Research only: official Google documentation/source and official Expo documentation, plus read-only inspection of this checkout and its existing debug APK. No app changes, builds, dependency/model downloads, installs, credential/account access, or device inference. Facts below describe current published documentation; recommendations and estimates are engineering judgment.

## Decision

**Technically yes, as two separate capabilities.** Ship-worthy OCR is broadly feasible; genuine scene description is feasible only on supported AICore/Gemini Nano devices, after model preparation. Neither requires sending the photo to a server. Image Labeling is categorization, not a description generator. Recommend **Extract Text** first, then a separately gated **Suggest Description** experiment. Do not promise description assistance on every Android phone. [Google OCR overview](https://developers.google.com/ml-kit/vision/text-recognition/v2), [Image Labeling](https://developers.google.com/ml-kit/vision/image-labeling/android), [Gemini Nano architecture](https://developer.android.com/ai/gemini-nano).

**Material release constraint:** Google's GenAI additional terms require API users to be 18+ and prohibit API clients directed toward or likely to be accessed by under-18s. This is broader wording than simply hiding a button from minors. Technical feasibility does not establish that Caelum can distribute this feature under those terms; resolve applicability with Google/appropriate legal review before release. The terms allow production clients but separately prohibit services designated Preview/Experimental Access from production. This finding concerns GenAI, not a claim that ordinary OCR has the same age restriction. [GenAI terms, Age Requirements and Use Restrictions](https://developers.google.com/ml-kit/genai-terms).

## Which API does what?

| API | Useful result | Published Android dependency / maturity |
| --- | --- | --- |
| Text Recognition v2 | Verbatim text with block/line/word structure, geometry and recognition metadata; no scene interpretation | Bundled `com.google.mlkit:text-recognition:16.0.1`; Chinese/Devanagari/Japanese/Korean variants also `16.0.1`. Stable/GA, not generative. |
| Image Labeling, default model | 400+ category labels with scores/indices, e.g. object/scene tags; cannot express reliable relationships or narrate a scene | Bundled `com.google.mlkit:image-labeling:17.0.9`; Play services `com.google.android.gms:play-services-mlkit-image-labeling:16.0.8`. Stable, not generative. |
| GenAI Image Description | One short English description; Google explicitly lists alt text as a use case | `com.google.mlkit:genai-image-description:1.0.0-beta1`; beta, without SLA/deprecation guarantees. Gemini Nano through AICore. |
| Optional Prompt API / direct model access | Image + custom instruction, optionally OCR text, producing text/structured output; more control and QA effort | `com.google.mlkit:genai-prompt:1.0.0-beta5` in latest release table; beta. Not necessary for the initial two actions. |

Sources: [OCR output structure](https://developers.google.com/ml-kit/vision/text-recognition/v2), [labeling integration](https://developers.google.com/ml-kit/vision/image-labeling/android), [Image Description guide](https://developers.google.com/ml-kit/genai/image-description/android?hl=en), [direct model access comparison](https://developers.google.com/ml-kit/genai/prompt/android), [latest versions/release history](https://developers.google.com/ml-kit/release-notes). “Cannot narrate” is the engineering implication of a category-label interface, not a Google accuracy guarantee.

**Documentation conflicts to preserve:** OCR Android page's generated summary says API 21+, while its normative “Before you begin” requires **23+**; use 23 as the planning floor. Some overview material still calls Text Recognition v2 beta, but the release history records its graduation to GA. Prompt's get-started snippet still uses **beta4**, while the October 26, 2026 release table and function-calling page use **beta5**. Prefer the latest release table, then verify the resolved artifact/manifest during a future implementation. [OCR guide](https://developers.google.com/ml-kit/vision/text-recognition/v2/android), [general guide](https://developers.google.com/ml-kit/guides), [release notes](https://developers.google.com/ml-kit/release-notes), [Prompt setup](https://developers.google.com/ml-kit/genai/prompt/android/get-started), [function-calling setup](https://developers.google.com/ml-kit/genai/prompt/android/function-calling).

## Local inference, setup and offline startup

Standalone ML Kit on-device APIs are available at no cost, with no Firebase project required. These integration paths require native Maven dependencies, not a cloud API key, billing account or Firebase configuration. Legacy “ML Kit for Firebase,” Firebase ML/Cloud Vision and Firebase AI Logic hybrid inference are different products/paths; do not copy their setup into this feature. Google's current migration page also announces Firebase ML shutdown on June 15, 2027. [Migration FAQ and current notice](https://developers.google.com/ml-kit/migration).

**Local is not network-silent.** Google says ML Kit keeps input images/text and resulting outputs on-device, but contacts servers for models, fixes/configuration and sends performance/utilization metrics. Disclosures include device/app information, identifiers, latency, API configuration, input/output sizes, feature events/errors, and GenAI configured languages. Therefore “photo processed on your phone” is supportable; “nothing ever leaves your phone” is not. [Terms/privacy](https://developers.google.com/ml-kit/terms), [Android data disclosure](https://developers.google.com/ml-kit/android-data-disclosure).

**OCR:** bundled models are present immediately, including after a fresh offline install; estimate **4 MB per script per architecture**, versus about **260 KB** client overhead for the unbundled option. Play services OCR models need installation first: manifest install-time requests after Play Store installation, explicit `ModuleInstallClient`, or first-use download. Calls before readiness produce no results, which must not be shown as “no text found.” Current Play services versions are Latin `19.0.2`, other four scripts `16.0.2`. [OCR Android integration](https://developers.google.com/ml-kit/vision/text-recognition/v2/android).

Bundled OCR is the recommended offline-first choice: a slightly larger app in return for predictable first use. Its models live with the app and update through app updates; unbundled models are shared/managed in Play services storage and updated independently. Bundling avoids that Play-services model-delivery dependency; actual non-GMS-device behavior remains a validation item, not something tested here. [Installation/storage comparison](https://developers.google.com/ml-kit/tips/installation-paths).

**Generative:** AICore owns model distribution/updates; models are shared across clients, with task-specific adapters. There is no documented APK-bundling option for Gemini Nano through these APIs. A fresh offline device without assets/configuration cannot be promised working descriptions. The API exposes download progress, including bytes to download; obtain readiness first, then allow an explicit user-approved setup download instead of letting inference implicitly start one. Exact stable-model/adapter storage size, eviction behavior, download policy and latency across phones are not specified sufficiently to quote a universal number. Budget device storage and failures explicitly. [AICore architecture/distribution](https://developer.android.com/ai/gemini-nano), [ImageDescriber download contract](https://developers.google.com/android/reference/com/google/mlkit/genai/imagedescription/ImageDescriber).

Google's preview guide calls models relatively large and requires Wi-Fi for **preview** downloads; that is not proof of the stable feature's universal transport policy. Preview enrollment and quota bypass are testing facilities, not normal consumer onboarding requirements. [AICore developer preview](https://developers.google.com/ml-kit/genai/aicore-dev-preview).

## What phones and languages actually benefit?

- **OCR:** no Gemini Nano phone allowlist. Plan for Android API 23+ and the scripts actually shipped. Latin covers English, Spanish, Catalan, French, German and many others. Additional recognizers cover Chinese, Devanagari, Japanese and Korean. Do not promise Arabic, Cyrillic, Thai or every language merely because the app translates its UI; Google's language table distinguishes supported, experimental and mapped coverage. [Language/script matrix](https://developers.google.com/ml-kit/vision/text-recognition/v2/languages).
- **Description:** published SDK floor **API 26**, plus supported hardware/AICore/model configuration. Current task-API allowlist includes the explicitly named Pixel 9/10/11 variants, Galaxy S25/S26 and selected recent Z models, OnePlus 13/13s/15/15R, and selected Honor, iQOO, Motorola, OPPO, POCO, realme, Redmi, Sharp, Sony, vivo and Xiaomi devices (also selected tablets/Googlebooks). **Consult the “Text and image task device support” list, not the separate custom-generation list.** Do not extrapolate to Pixel 8, Pixel a-series, Galaxy S24, every flagship or every model in a brand. [Current task-specific allowlist](https://developers.google.com/ml-kit/genai#feature-device).
- Runtime `ImageDescriber.checkFeatureStatus()` is definitive for the requested configuration: `UNAVAILABLE`, `DOWNLOADABLE`, `DOWNLOADING`, `AVAILABLE`. Even a listed phone can lack readiness. Output is currently English only and short; hardware/model variation changes results. An English draft may be useful to a multilingual author but is not native-language ALT assistance. [Image Description limitations/runtime checks](https://developers.google.com/ml-kit/genai/image-description/android?hl=en).

The API-level floor is not a promise of Nano on Android 8. Contemporary supported physical hardware is the relevant target. Likewise do not apply the separate agent workflow's Android 14/API 34 + developer-preview prerequisites to the task-specific Image Description API. [Agent prerequisites](https://developers.google.com/ml-kit/genai/agent/android/get-started).

**Engineering assessment:** most existing Caelum Android users could benefit from OCR if their images use supported scripts; description benefit is a subset on Google-supported devices. The actual percentage is unknown without a device census, and none was accessed. The supplied x86_64 Android 15 standard Google APIs emulator is not evidence of AICore support: no supported emulator workflow was established in the official docs inspected. It can exercise OCR/UI/unavailable paths; GenAI quality, offline behavior and latency remain unverified until tested on supported physical hardware. Android version or a Pixel-shaped emulator profile alone proves nothing.

## Operational and ALT-text limitations

GenAI inference must run in the **top foreground app**, including no workaround through a foreground service. Short-term excess requests return `BUSY`; long-duration battery quota can return `PER_APP_BATTERY_USE_QUOTA_EXCEEDED`. Google publishes no universal requests-per-minute/day entitlement. [Foreground/quota rules](https://developers.google.com/ml-kit/genai#quota-per).

Unlocked bootloaders are explicitly unsupported. New/reset phones or reset AICore installations may need configuration/model preparation and can fail binding or feature discovery for minutes to hours. Preserve manual editing and offer a later retry. [Setup issues](https://developers.google.com/ml-kit/genai/image-description/android?hl=en#common-setup-issues).

Other documented failures include insufficient storage, incompatible AICore, system update needed, invalid images, and policy-filtered requests/results. The inspected error reference does not establish a fixed thermal cutoff or separate thermal error contract: thermal slowdown/pressure and energy use are validation risks, not measured facts here. Use one request at a time, no automatic retry loops or batch-on-import generation; measure cold/warm latency, heat and battery on real phones. [Error contract](https://developers.google.com/android/reference/kotlin/com/google/mlkit/genai/common/GenAiException.ErrorCode).

OCR quality depends on focus, text pixel size and orientation. It transcribes visible text; it does not explain a chart, meme, layout or visual relationship. [OCR image guidance](https://developers.google.com/ml-kit/vision/text-recognition/v2/android#input_image_guidelines). Descriptions may invent or omit details and lack the author's context; they should not infer identity, intent or sensitive characteristics. Google warns that generated content can be inaccurate/offensive; Prompt quality must be evaluated per model version. **Review before apply is mandatory product design judgment**, not a guarantee that review eliminates errors. [GenAI content disclaimer](https://developers.google.com/ml-kit/genai-terms), [Google evaluation guidance](https://developers.google.com/ml-kit/genai/prompt/android/evaluate-prompt).

## Fit with this checkout and a thin native boundary

Read-only repo findings:

- [ImageAltTextDialog.tsx](../src/view/com/composer/photos/ImageAltTextDialog.tsx) owns controlled edit state inside `ImageAltTextInner` deliberately: moving it above the portal causes delayed input commits. The outer `editedAltText` ref tracks changes; `onClose` commits them using `enforceLen`. Keep suggestions/review state inside the inner component and update both controlled state and the existing edit callback only on explicit Apply. Merely generating/closing must not commit a candidate. Use existing dialog close callbacks for post-close actions.
- Analyze **`image.transformed ?? image.source`**, matching the displayed crop. [gallery.ts](../src/state/gallery.ts) (the requested `.tsx` path does not exist) defines `ImageMeta.path`, dimensions/MIME, optional transformed metadata and cache copying. Inputs can originate as local file paths/URIs; initial/paste paths are less constrained. Validate supported local inputs, rotation, decoding, memory bounds and cache lifetime; do not silently fetch a remote URL. [Constants](../src/lib/constants.ts) sets `MAX_ALT_TEXT = 2000`; review character limits and truncation before applying, especially OCR.
- [Existing local module](../modules/expo-receive-android-intents/android/src/main/java/xyz/blueskyweb/app/exporeceiveandroidintents/ExpoReceiveAndroidIntentsModule.kt) demonstrates Kotlin `Module`/`ModuleDefinition`; its [registration](../modules/expo-receive-android-intents/expo-module.config.json) and [Gradle file](../modules/expo-receive-android-intents/android/build.gradle) establish the local Android-only module pattern. A small separate module is feasible; no RN bridge rewrite is indicated. Expo supports Kotlin async functions, events and lifecycle cleanup. Native changes require a rebuilt native app. [Expo Modules overview](https://docs.expo.dev/modules/overview/), [module API](https://docs.expo.dev/modules/module-api/).
- No ML Kit dependencies were found in `package.json`, `pnpm-lock.yaml` or module sources. [package.json](../package.json) declares Expo `58.0.23`, RN `0.88.1`, React `19.3.0`, a `typescript` alias targeting TypeScript 6, and an `@typescript/native` alias targeting TypeScript 7. No TS-version blocker is indicated for a typed native wrapper.
- Existing `android/app/build/outputs/apk/debug/app-debug.apk`, inspected with installed `aapt dump badging`, reports **minSdk 24, targetSdk 36, x86_64**. This describes that artifact, not a release guarantee. OCR fits its floor; documented GenAI dependencies require 26. Raising the whole app floor would drop API 24/25 users; preserve them with OCR/manual through a deliberately designed build strategy or accept the floor increase. Runtime gating alone does not bypass a manifest dependency minimum. No dependency was downloaded to verify merging/transitive compatibility.

Proposed boundary (design only): `getCapabilities()` / `getStatus(feature, script)` returning readiness and reason; `download(feature)` with progress; `cancel(requestId)`; `recognize({requestId, uri, script})` returning text plus optional blocks; `describe({requestId, uri})` returning a draft; resource cleanup on dialog/module teardown. OCR bundled readiness is distinct from GenAI feature status. The native description client already provides status/download/inference/close methods. **Cancellation caveat:** its public surface returns `ListenableFuture` but documents no dedicated cancel-download method or guaranteed service-wide cancellation. Cancel local work/futures where supported and suppress stale results; verify actual cancellation semantics before claiming a download or inference physically stopped. [ImageDescriber reference](https://developers.google.com/android/reference/com/google/mlkit/genai/imagedescription/ImageDescriber).

Recommended UI: **Extract Text** and **Suggest Description**, explicit progress/error states, then an editable candidate preview and Apply/replace-or-append choice. Never overwrite text typed while work was running. Keep manual entry on unsupported Android, web and iOS; this memo makes no claim of an iOS GenAI API. No cloud fallback, upload or hybrid routing without separate explicit user permission. Google's hybrid option can automatically route to cloud, so it is inappropriate as an implicit fallback here. [Google's hybrid description](https://developer.android.com/ai/gemini-nano#hybrid-inference).

## Effort and next decision

**Engineering estimates, one engineer familiar with this repo; not vendor promises:** bundled Latin OCR plus review UI, cancellation/stale-result handling and targeted tests: **2–4 engineering days**. Adding task-specific GenAI status/download/errors and supported-phone evaluation: **another 4–8 days**, assuming immediate physical-device access and resolved terms/minSdk decisions. Combined release-quality work: approximately **1.5–3 working weeks**, excluding approval/legal clarification, hardware procurement and Google rollout delays. More scripts add packaging/language QA; custom Prompt-based output adds approximately **3–7 further days** for prompt design/evaluation and native compatibility work, without assuring better ALT text.

Proceed with OCR feasibility first. Treat descriptions as conditional on distribution terms, SDK-floor strategy and a physical-device trial demonstrating useful English drafts and truly offline inference after preparation. Remaining unknowns are actual Caelum device coverage, download/storage footprints, merged build compatibility, cancellation behavior, real latency/thermal/battery performance and accessibility quality across representative photos, screenshots, charts and memes.
